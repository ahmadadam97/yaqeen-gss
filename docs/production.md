# How this would run at full scale

This is a design sketch for bonus 4.5, not a deployment. Today the local batch has 7,753 interviews, two public files, and one operator. There is no demonstrated need for an always-on service. Move to managed storage and compute when concurrent readers, refresh deadlines, or measured memory use justify it.

| Decision | Proposed AWS operation | Tradeoff |
|---|---|---|
| Storage and compute | Keep immutable source objects in versioned, encrypted S3 prefixes by source and release, plus a checksum manifest. Run Python and dbt in an ECS Fargate task. For concurrent analysts, use Redshift Serverless with a dbt Redshift profile and typed staging columns. Re-test DuckDB-specific JSON, pivot and aggregate SQL before migration. | Pays for managed warehouse compute, but separates analytical reads from ingestion. For a single periodic run, keep DuckDB. |
| Trigger and recovery | EventBridge Scheduler starts a Step Functions workflow after a source release is expected. Run one ECS task at a time per release. The task fetches the manifest, loads, builds, tests and publishes in that order. Key reruns by release/hash; quarantine conflicts. Retry transient service failures, never retry a schema disagreement as though it were a network error. Keep the last tested release available until the replacement passes. | A scheduled manifest check tolerates late or repeated deliveries. Continuous streaming adds little to infrequent survey releases. |
| Access and monitoring | Separate scheduler, task and analyst roles. The scheduler can start that workflow; the workflow can run only the named task and pass its roles. The task reads approved S3 prefixes and writes to staging; the publisher promotes tested analytics. Analysts read published views only. Use KMS encryption, private networking, short-lived role credentials and CloudWatch logs/alerts with release, counts, rejected files and duration. | Keep access to sensitive survey microdata separate from public aggregate results. Do not log responses or join people to donor records. |
| Cost and growth | At full GSS size the dense interview-by-variable table approaches 530 million rows. Track rows expanded, bytes scanned, Fargate CPU/memory duration, Redshift compute time, S3 versions and log retention. Start with required variables and partition columnar staging by wave; replace only affected waves and run the same tests. | Keep original releases so corrections are auditable. Pay for incremental processing only once full rebuilds miss the refresh or cost target. |

**Additional sources and contracts.** These are proposed inputs, not data used in this submission.

- **Pew Religious Landscape Study:** For an external check on comparable faith items, ingest the public-use file and questionnaire once per release, subject to its access and citation terms. Assume one release fits a batch. Keep the original, release-specific item codes and weight; map only compatible question wording/universes to a shared concept. Key interviews by (source, release, local ID). Publish separately labelled estimates; never join individual respondents across surveys. [Dataset and access limits](https://www.pewresearch.org/dataset/2023-24-religious-landscape-study-rls-dataset/).
- **Yaqeen format pilot:** If permission and data exist, ingest weekly aggregate totals by content, format and week, with starts/completions and a versioned definition of completion. Agree what counts as a start and a completion before collecting data. Check uniqueness and that completions belong to the same start cohort. Store no religion, donor identity or visitor identifiers in this reporting table; suppress small breakdowns per an agreed policy. Compare formats within a common pilot, with consistent traffic assignment and observation windows. General web use in GSS cannot substitute for this measure.

See [AWS task orchestration](https://docs.aws.amazon.com/step-functions/latest/dg/connect-ecs.html) and [Yaqeen's mission and formats](https://yaqeeninstitute.org/about-us/our-mission).
